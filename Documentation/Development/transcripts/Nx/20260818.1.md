⏺ I'm oriented. Here's my working model of the two modes you want to modify:

  Automatic (AutomaticController + AutomaticConfig) — the anti-throttle control
  law. Per tick it:
  - Takes the hottest of CPU/GPU, computes a proportional ramp from
    target→ceiling (per power source).
  - Adds an anticipation boost on dT/dt, gained by spikeResponse (0–1).
  - Applies a max override to 100% when thermalState is .serious/.critical or
    temp ≥ ceiling, held 5 s.
  - Smooths asymmetrically: rises instantly, decays ≤ 0.15/s to avoid hunting.
  - Emits one fraction (0–1) applied to every fan.

  Adaptive (FanCurve / FanCurveConfig) — per-power-source curve sets, one
  FanCurve per ThermalSource (cpu/gpu/battery). Each maps temp→% via a monotone
  cubic spline (linear under 3 points), and the engine takes the max across 
  enabled curves ("highest safety wins"), yielding one fraction.

  Shared plumbing (FanController): targets(for:) turns that fraction into
  per-fan RPM within each fan's [min, max] bounds; writes go through the helper
  only past the reapplyDeadbandRPM (50) deadband; temps are refreshed every 2 s
  tick (full snapshot only when UI is visible). Config lives in AppState
  (persisted to UserDefaults), edited live in ConfigView's Automatic/Adaptive

  Why the fans hold at minimum today

  There are two independent floors keeping you off 0-RPM, and both would have to
  be addressed:

  1. App-side floor — FanController.fraction(_:of:) (FanController.swift:278)
     maps a 0-fraction to bounds.minRPM, not 0. So even when Automatic decays to
     0 or an Adaptive curve reads 0% (its default CPU knee is 40°C → 0%), the
     commanded target is the fan's minimum, never off.
  2. Helper-side clamp — even if the app commanded 0, FanSMC.setManual
     (FanSMC.swift:39) does clamped = max(minRPM, min(maxRPM, rpm)), so the
     target can never go below F{i}Mn.

  The hard constraint

  F{i}Mn is a firmware-enforced minimum for manual targets. On Apple Silicon,
  the only thing that drives a fan below Mn — all the way to off — is the SMC's
  own auto controller (what runs in Disabled mode). Writing a manual target
  below Mn, even under the Ftst unlock gate, is almost certainly clamped by
  firmware. So removing our own two clamps likely won't get you to 0; the
  firmware just re-imposes Mn.

  I'd put ~85% confidence on that. It's cheap to confirm empirically before
  committing to a design — a temporary DEBUG-only probe in the helper that,
  under Ftst, writes a sub-Mn target (say Mn/2, then 0) and reads back F{i}Ac a
  few seconds later. If actual RPM clamps to Mn, direct 0-RPM is off the table;
  if it genuinely drops, that changes everything. dumpFanKeys already gives us
  the inspection primitive. Want me to write that probe first?

  What I recommend regardless: hand back to macOS when cool

  This is your second idea, and I think it's the right one — it reaches genuine
  0-RPM (macOS turns them fully off) using a path we already trust. But one
  important detail makes it cleaner than the per-fan kFanTargetAuto sentinel:

  - Per-fan setAuto (FanSMC.swift:46) only writes mode=0; it leaves Ftst raised.
    With test-mode still engaged, the firmware may not truly idle the fan to 0.
  - releaseControl() → releaseAll() (FanSMC.swift:52) returns every fan to auto
    and clears Ftst — full firmware control restored. This is the exact path
    Disabled/sleep/quit already use, and CLAUDE.md confirms lid-close-release +
    wake-resume works through it.

  So for a full spin-down I'd reuse helper.releaseControl(), not per-fan -1
  targets. Since both modes drive all fans from a single scalar fraction today,
  "all fans off vs all fans engaged" is the natural granularity anyway.

  Mechanism (lives entirely in FanController, no helper or protocol changes):
  - A small hysteresis state machine on the computed fraction: hand off when
    frac ≈ 0 (release to macOS), re-engage manual control when frac rises past a
    margin (e.g. ~5%).
  - Asymmetric by design: entry into handoff can have a short dwell to avoid
    flapping, but exit is instant — the moment the controller wants airflow
    (including the thermal-pressure override jumping to 1.0), we re-take control
    on the next tick with no dwell. We're only ever lazy about releasing, never
    about grabbing back.
  - Temps keep flowing while released because both modes are needsTemperature,
    so the re-engage decision always has fresh readings even with no UI open.

  This actually strengthens the safety invariants: the cool-idle state is "fans
  on macOS auto," so an app crash while spun-down leaves the machine in the safe
  state, and the watchdog naturally sees engaged=false.

  Points I'd like your read on

  1. Handoff vs. holding out for direct 0-RPM — I recommend handoff as the
     design even if the probe surprises us, because it's robust and
     firmware-agnostic. Agree, or do you want the probe result to gate the
     decision?
  2. The tradeoff it carries: while spun-down, our anticipation/spike-response
     logic is dormant and macOS's (lazier) auto governs. That only happens when
     the machine is genuinely cool — far from throttle — and we re-engage with
     margin, so I think it's a clean trade. Comfortable with that?
  3. Hysteresis anchor — I'd anchor on the fraction (mode-agnostic, simple).
     Alternatively I can anchor on temperature per mode ("fans stop below X°C")
     which is more legible in the UI but more code. Preference?
  4. UX — make it inherent behavior, or expose an "Allow fans to stop when cool"
     toggle (default on) per mode? Given this was the deferred "0-RPM
     investigation," a default-on toggle lets cautious users opt out.

  The 8-minute tail: it was macOS, not us

  Short version: BreezyMac released control back to macOS within ~15–20 seconds 
  of your die temps dropping below the 70 °C target. Everything after that — the
  ~8 minutes at ~2300 RPM and the eventual drop to 0 — was macOS's own fan 
  controller.

  Here's the chain of reasoning, which is deterministic enough that I'm
  confident:

  1. Our fraction decays to zero in ~8 s. When temp falls below target,
     Automatic's proportional term is 0 and (temp falling) the anticipation term
     is 0, so base = 0. The asymmetric smoothing then decays the commanded
     fraction at decayPerSecond = 0.15 — about 0.30 per 2 s tick — so from full
     it reaches ~0 in roughly four ticks (~8 s).
  2. Handoff fires ~10 s later. Once the fraction is ≤ 0.02, the
     handoffSettleSeconds timer runs and, ~10 s after, releaseControl() hands
     all fans to macOS and clears Ftst. Total: ~18 s after crossing below
     target. You reported temps were already <50 °C by 45 s, so we'd almost
     certainly handed off inside the first minute.
  3. The rest is macOS, and it's a thermal-mass story. The sensors we read
     (Tp*/Tg*) are on the CPU/GPU die — tiny thermal mass, so they cool within
     seconds when load ends. But that energy soaked into the heatsink and 
     chassis — large thermal mass — which stays hot for minutes. macOS tracks
     those broader sensors (which we don't drive fans from), so it kept minimum
     airflow to evacuate the stored heat, then stopped the fans once the whole
     assembly cooled. Your UI showed the actual fan RPM (F{i}Ac) the entire
     time, regardless of who was in control — so it looked like "our" minimum,
     but it was macOS's.

  So this is not a stall or a bug — it's design decision #2 doing exactly what
  we intended ("macOS governs while spun-down"), and here it gave better cooling
  than forcing 0 RPM ourselves would have, because macOS sees the heat we
  can't. I documented this in CLAUDE.md so it doesn't get mistaken for a defect
  later.

  it'd print the exact release and re-grab timestamps, so you'd see the ~18 s

  What was happening

  The popover width was hard-pinned: .frame(width: 340). The segmented mode
  Picker is the widest row, and its four labels are longer in some locales
  (Portuguese Desativado / Automático / Adaptável / Desempenho) than in English.
  At a locked 340pt the control couldn't get the width it needed, so the
  segments clamped/overflowed.

  The fix (PopoverView.swift, lines 53–64)

  Two one-line changes to the outer container:

  - .frame(width: 340) → .frame(minWidth: 340) — 340 becomes a floor, not a cap.
  - .fixedSize(horizontal: false, vertical: true) → .fixedSize() — the view now
    hugs its content in both axes, so it reports its true ideal width (≥ 340)
    rather than stretching to a proposed width.

  This works because the plumbing was already right for it:
  NSHostingController.sizingOptions = [.preferredContentSize] and no hard-coded
  popover.contentSize, so the popover simply adopts whatever intrinsic size the
  SwiftUI view reports.

  Resulting behavior:
  - English and any locale whose picker fits ≤ 340 → width stays exactly 340,
    identical to before.
  - Portuguese / any longer locale → the popover grows just enough to show the
    mode buttons in full, never shrinking below 340.
  - The charts and the header/footer Spacers are horizontally flexible, so they
    simply fill whatever final width the picker drives — no other row forces
    extra width.

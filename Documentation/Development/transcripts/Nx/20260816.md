❯ We are going to create a new macOS application from scratch. It will be       
  called "BreezyMac" with an app/bundle ID of `org.WhoCo.BreezyMac`. Its        
  purpose is to implement fan control for M-series MacBook hardware.            
                                                                                
  Inside the `Reference` directory, there are 2 projects that implement similar 
  capabilities. They both implement a form of fan control with varying degrees  
  of capability and stability.                                                  
    - The `Reference/ShahzaibAli02.Fanny-MacOs-FanControl` application          
  implements fan control and appears to do it properly, according to recent     
  macOS version requirements. It's handling of the fan seems unstable and a bit 
  buggy. We should leverage this application's fan control infrastructure as a  
  roadmap to re-implementing a bug-free implementation. It also implements fan  
  curves, and we should use this implementation as a roadmap for our own.       
    - The `Reference/idevtim.chillmac` application has a much more elegant user 
  interface, but the implementation of fan control seems to be broken. We       
  should leverage its UI infrastructure as a reference to implementing a        
  similar user interface concept.                                               
                                                                                
  Our goal is to implement a fan control application. The application           
  front-end/UI will consist of a configuration tool window with tabbed          
  sections, and a status bar icon. The configuration window is not shown by     
  default; Only the status bar icon is visible normally. Under normal           
  operation, no icon should be shown in the macOS dock; Only the status bar     
  icon should be shown.                                                         
    The application back-end will consist of a helper service that is           
  responsible for the actual fan control.                                       
                                                                                
  The application will be *exclusively* concerned with system temperatures and  
  fan control. It will not have any UI for battery charge status, memory usage, 
  hard drive status, etc. The CPU/GPU activity/usage *can* be used by the fan   
  control algorithm to prognosticate fan control requirements, and therefore,   
  may have a minimal representation within the UI. We will discuss the exact    
  representation as UI elements when we get to that section.                    
                                                                                
  The application will have 4 operating modes:                                  
    - "Disabled": The application and helper are completely disabled and have   
  no influence over fan control or any other system. In this mode, all control  
  *must* be returned to the operating system gracefully.                        
    - "Silent": All fans are turned off and kept off, regardless of system      
  load. Fan curve logic is ignored.                                             
    - "Adaptive": Fans are controlled by a curve relative to CPU/GPU/system     
  thermals.                                                                     
    - "Performance": All fans are kept at *maximum*, regardless of system load. 
  Fan curve logic is ignored.                                                   
                                                                                
  The status bar icon source image is located at `assets/app_icon.png`. The     
  `assets` Directories should be used for all final production images with      
  proper organizational directories. The `assets` folder within the `Reference` 
  directory should be ignored; It is for source. Images that are still work in  
  progress, or otherwise not used in the production build.                      
                                                                                
  Requirements:                                                                 
    - Targets macOS 25+.                                                        
    - The application must use the Swift programming language.                  
    - Support for multiple languages/cultures starting with English (US/UK),    
  Spanish, Chinese, Korean, German, French, and Portuguese.                     
    - When the UI application is not active, the back-end helper must be        
  completely disabled and gracefully return all fan control to the operating    
  system. The back-end helper **must not have any influence on any system fan   
  control when the UI is not active and connected**.                            
    - The fan control *must not have any influence on the system when the       
  device is going to sleep mode*. The back-end helper must be completely        
  *disabled* when the laptop lid is closed.

  FourCharCode packing.
  - Keys: read FNum, F{i}Ac/Mn/Mx/Tg, F{i}ID, temp fallback lists; write

  gate), FS! (Intel bitmask).
  - Apple-Silicon unlock sequence: mode-key case-probe → direct mode write (M5+)
  → else Ftst gate + retry (M1–M4) → encode target as flt/fpe2.
  - The rules engine model: threshold + linear min/max curve, max-wins,
  auto-restore when cool.

  Must-fix gaps (these map directly onto your hard requirements):
  - Fanny has no reset-on-quit, no crash safety, and no sleep/wake/lid handling
  — fans can stay locked forever. Our design must have applicationWillTerminate

  to OS-auto the instant the app disconnects or the lid closes.
  - Replace the setuid-root CLI + per-command process-spawn (a privesc footgun,
  40 forks/min) with a resident privileged helper over XPC holding one SMC
  connection.

  2. Automatic mode — the design that matters most

  Your framing (hold temps under the throttle threshold with margin; slam to max
  if throttling starts) is exactly a setpoint controller with a 
  thermal-pressure override. Concretely:

  - Proactive ramp: fan fraction rises with (T − T_target) / (T_ceiling − 
  T_target), taking the max of the CPU- and GPU-derived values — plus a rate 
  term: if temperature is climbing fast (high dT/dt), pre-boost before it
  reaches the setpoint. That rate term is what buys the margin against spikes.
  - Throttle override → max: here's the honest constraint — Apple Silicon 
  exposes no clean public "throttling now" flag. The official proxy is
  ProcessInfo.thermalState (.nominal / .fair / .serious / .critical), which
  reflects system thermal pressure. So Automatic goes 100% whenever thermalState
  ≥ .serious OR any temp ≥ T_ceiling, and eases back (with a short hold to
  avoid flapping) once both clear. I'd avoid CPU-frequency-based throttle
  detection — it needs private APIs.
  - Power-aware setpoints: on AC, prioritize cool (e.g., start ramping ~80°C,
  full by ~95°C); on battery, raise the setpoint so fans stay quiet longer to
  save power (e.g., ~90°C → ~100°C), still catching real throttling.
  - Asymmetric response: ramp up fast, decay slow — prevents oscillation.
  - Defaults are tuned so most users never open the knobs;
  target/ceiling/aggressiveness live in an advanced section.
